# 시스템 아키텍처 전략

- 횡단 기능을 다루는 **단일 기준**. `system-architect`가 이 규칙으로 판단한다.
- 계층 전략(core/bridge/ui-design-strategy)=각 계층의 생산 규칙, 이 전략=세 계층을 가로질러 **먼저 구조를 잡는 사전 설계** 규칙. verify-strategy(배포 직전 게이트)와 짝이되 이쪽은 **착수 이전** 게이트다.

## 0. 핵심 원칙

1. **횡단 먼저.** 시스템 전반 기능을 한 계층 관점으로 들어가면 임시방편이 나온다. 전 계층을 가로질러 구조를 먼저 본다.
2. **분석→전반설계→분해 순서 고정.** 구현 설계로 바로 뛰지 않는다.
3. **읽기 전용.** 아키텍트는 측정·설계만 한다. 소스·설정 수정 금지. 구현은 매니저(core/bridge/ui-manager)로 인계.
4. **단일 소스 존중.** 계층 세부 규칙은 각 전략을 **참조**한다. 재정의 금지.
5. **종단간 추적.** 모든 결론은 요구→ui→bridge→core→설정 키가 끊김 없이 이어지는 RTM으로 닫는다.
6. **단방향 인계·세션 분리.** 인계는 core→bridge→ui. 분석·설계와 구현은 세션을 나눈다.

## 1. 횡단 판별 기준

| 신호 | 횡단(이 전략) | 단일(매니저) |
|---|---|---|
| 건드리는 계층 수 | 2개 이상 | 1개 |
| 입력 상태 기계(`src/state/`) | 상태·전이 자체를 바꿈(새 상태 추가, 타이머 의미 변경) | 파라미터(초·횟수)만 |
| 계약 | 기존 command·event 필드 제거·의미 변경 | 필드 추가·새 command |
| 설정 JSON | 스키마 버전 승격·마이그레이션 | 키 1개 추가(기본값 있음) |
| 데이터 흐름 | hook→event→state→overlay 경로 자체 변경(예: 스로틀 위치 이동) | 한 지점의 버그 |
| 증상 | 같은 판정 로직이 Rust와 TS에 중복 | 국소 결함 |

- 단일이면 즉시 해당 매니저로 안내한다(화면=ui-manager, 계약=bridge-manager, 네이티브=core-manager).
- 애매하면 영향 후보(모듈·계약·화면)를 훑어 계층 수를 센 뒤 판정한다.

## 2. 3단계 방법론

### 2.1 구조 분석 (현황, 읽기 전용)
- `core-analyst`·`bridge-analyst`를 **병렬 위임**해 현황·표준 준수·영향을 받는다(요약 + 리포트 파일 경로).
- ui는 직접 읽는다: 화면 `design.md`, `src/state/*.ts`, `src/bridge/*.ts`.
- 산출: **구조 분석서** — 현재 데이터 흐름 다이어그램(텍스트), 계약 목록, 상태 기계(상태·이벤트·전이·타이머), 설정 스키마, 문제점·제약·중복.

### 2.2 전반 설계
- 요구를 종단간으로 재정렬한다. 대안이 갈리면 근거를 양쪽 다 적고 사용자 결정(`AskUserQuestion`).
- 판단 기준 예: 판정 로직은 **한 곳**(원칙: 시간·횟수 판정은 TS 상태 기계, 원시 입력 정규화·스로틀은 Rust hook). 이미지 바이트는 이벤트에 싣지 않는다. 설정은 Rust가 소유하고 ui는 command로 읽고 쓴다.
- 산출: **전반 설계서** — 목표 구조, 상태 기계 확정본, 계약 변경 목록(추가/변경/폐기 + 하위 호환 여부), 설정 스키마 변경(버전·마이그레이션), 종단간 RTM.

### 2.3 계층별 구현 설계 분해
- 계층마다 **인계 패킷** 1개. 각 패킷은 그 매니저가 **그것만 읽고** 시작할 수 있어야 한다.

## 4. 종단간 RTM

| 요구ID | 요구 | ui | bridge | core | 설정 키 | 테스트 | 상태 |
|---|---|---|---|---|---|---|---|

- 어느 열이든 끊기면 미완. 해당 없음은 `-`.

## 5. 인계 규약

- 순서 **core → bridge → ui**. 앞 계층의 완료 마커가 뒤 계층의 착수 조건.
- 각 매니저 세션은 자기 패킷만 읽고 자기 전략으로 일한다. 패킷에 없는 것을 추측해 만들지 않는다 — 부족하면 아키텍트 세션으로 되돌린다(왕복은 아키텍트 세션에서만).
- 계약 파괴 변경은 bridge 패킷에 **하위 호환 전략**(동시 지원 기간·폐기 시점)을 명시한다.

## 6. 세션 분리

- 분석·설계(아키텍트) / core 구현 / bridge 구현 / ui 구현 / verify는 **각각 별도 세션**.
- 한 세션에서 두 계층을 구현하지 않는다(컨텍스트 50% 규칙).
